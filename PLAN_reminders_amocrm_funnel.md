# План: напоминания, интеграция с amoCRM, настраиваемая воронка

Составлен 2026-08-01. Три функции, заказанные владельцем продукта:

1. **Напоминания** — задавать срок актуальности задачи, частоту напоминаний (день/неделя) и время суток.
2. **amoCRM** — полная совместимость, включая двусторонний обмен.
3. **Воронка** — пользователь добавляет свои этапы к четырём базовым.

Порядок сборки: **A (воронка) → B (напоминания) → C (amoCRM)**. Воронка — самый малый кусок и она разблокирует
маппинг этапов для amoCRM; без неё воронки amo просто нечем представить.

## A. Настраиваемая воронка

Самая лёгкая из трёх: база уже готова, права уже прописаны, не хватает роутов и экрана.

### A.1 Миграция схемы

```prisma
model PipelineStage {
  // ... существующие поля ...
  probability      Int?      // % вероятности закрытия на этапе
  stale_after_days Int?      // «зависла», если стоит дольше N дней
  is_archived      Boolean   @default(false)  // скрыть, не удаляя историю
}
```

Инварианты переносим в БД, а не в приложение — частичные уникальные индексы:

```sql
CREATE UNIQUE INDEX pipeline_stage_one_won  ON "PipelineStage" (pipeline_id) WHERE is_won_stage;
CREATE UNIQUE INDEX pipeline_stage_one_lost ON "PipelineStage" (pipeline_id) WHERE is_lost_stage;
```

Уникальность на `position` **не добавляем** — она превращает перестановку в двухфазную пляску с временными
отрицательными значениями. Позиции нормализуем в транзакции.

### A.2 Эндпоинты

Гейт `deals.stage_admin` → `org.manage` уже существует (`authenticate.ts:54`), роли подхватятся сами.

| Метод | Путь | Поведение |
|---|---|---|
| `POST` | `/api/v1/deals/stages` | создать этап `{pipeline_id, name, position?, color?, probability?}` |
| `PATCH` | `/api/v1/deals/stages/:id` | переименовать, цвет, вероятность, флаги won/lost |
| `DELETE` | `/api/v1/deals/stages/:id?move_to=<id>` | отказ, если есть сделки и не задан `move_to` |
| `POST` | `/api/v1/deals/stages/reorder` | `{pipeline_id, ordered_ids[]}` — одна транзакция |
| `POST/PATCH/DELETE` | `/api/v1/deals/pipelines` | CRUD воронок целиком (гейт тоже уже есть) |

### A.3 Защиты — без них ломается отчётность

1. Ровно один `is_won_stage` на воронку — частичный индекс + понятный 409. `reporting.ts` и
   `pipelineHealthScore` считают выигрыш именно по нему.
2. Нельзя удалить последний этап воронки.
3. Нельзя удалить этап со сделками без `move_to`.
4. Перестановка **не трогает `stage_entered_at`** — иначе все сделки разом станут «свежими»
   и отчёт о зависших обнулится.
5. Скоуп организации — переиспользовать `stageBelongsToPipeline` (`deal-domain.ts:118`).

### A.4 Библиотека этапов

В `backend/config/market.ts` рядом с `DEFAULT_PIPELINE_STAGE_NAMES`:

```ts
export const OPTIONAL_STAGE_LIBRARY = [ /* см. ниже */ ] as const;
```

**Предлагать по умолчанию (три штуки):**

| Этап | Куда | Зачем |
|---|---|---|
| **Переговоры** | между Квалификацией и Предложением | стандарт amoCRM, есть почти в каждой российской воронке |
| **Выставлен счёт** | после Предложения | разрыв между «договорились» и «оплатили» — где реально умирают деньги в B2B |

Отложено (Думает) · Первичный контакт · Отгрузка / Доставка · Повторная продажа.

## B. Напоминания + RuStore Push

### B.1 Часовой пояс — блокер, идёт первым

Без него «выбрать время суток» бессмысленно: 09:00 сейчас означает 09:00 UTC, то есть **12:00 в Москве**
(прод закреплён на UTC).

- `User.timezone String @default("Europe/Moscow")` — IANA-имя.
- Константу `DISPLAY_TIME_ZONE` (`notificationEngine.ts:94`) переносим в `market.ts` как `DEFAULT_TIME_ZONE`.
  Комментарий в коде на строках 88-93 прямо просит это сделать, «когда появится второй потребитель» —
  вот он и появился.
- `formatDate`/`formatTime` принимают пояс получателя.
- В онбординге и профиле — выбор пояса, по умолчанию берём с устройства.

### B.2 Схема — таблица `TaskReminder`

Отдельная таблица, а не новые колонки в `Task`: у задачи может быть несколько правил, и одноразовый
`reminder_at` продолжает работать без переписывания.

```prisma
enum ReminderFrequency { once daily weekly weekdays custom }

model TaskReminder {
  id              String   @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  task_id         String   @db.Uuid
  organization_id String   @db.Uuid
  recipient_id    String   @db.Uuid   // обычно assigned_to, но позволяет дублировать руководителю
  frequency       ReminderFrequency
  time_of_day     String              // "09:00" — настенное локальное время
  days_of_week    Int[]               // для weekly: 1=Пн .. 7=Вс
  timezone        String              // снимок пояса на момент создания
  starts_at       DateTime
  expires_at      DateTime?           // «сколько задача актуальна»
  next_fire_at    DateTime?           // материализованный UTC-момент — единственное, что сканирует планировщик
  last_fired_at   DateTime?
  fire_count      Int      @default(0)
  is_active       Boolean  @default(true)
  created_at      DateTime @default(now())
  updated_at      DateTime @updatedAt

  @@index([is_active, next_fire_at])
  @@index([task_id])
}
```

Миграция создаёт по одному `once`-напоминанию для каждой задачи с непустым `reminder_at`. Само поле
оставляем — его читает клиентское локальное уведомление и публичный API.

### B.3 Переписывание планировщика

`runReminders()` (`scheduler.ts:120`) переходит с окна `reminder_at ±30 с` на выборку по индексу
`next_fire_at <= now`.

**Это заодно чинит скрытую потерю напоминаний.** Сейчас пропущенное окно теряется навсегда: перезапуск
сервера или пропуск джоба по `runExclusively` — и напоминание не приходит вообще. Семантика «догоняем всё,
что просрочено» такого не допускает. Оборотная сторона: после долгого простоя прилетит пачка старых
напоминаний, поэтому нужен потолок — не догонять то, что просрочено больше чем на N часов.

- Претензия на отправку: ключ `task.reminder:<reminder_id>:<next_fire_at epoch>`. Существующая
  `claimScheduledPush` работает как есть, меняется только формат ключа.
- После отправки — пересчёт следующего срабатывания **в поясе напоминания**, с учётом перехода на
  зимнее/летнее время. `rrule` уже в зависимостях, но с поясами он капризен; рекомендую **luxon**.
- Деактивация при наступлении `expires_at` или закрытии задачи.
- **Батчинг**: ежедневное напоминание в 09:00 на всю организацию — это N пушей в одну секунду.
  Expo SDK умеет чанковать, RuStore-транспорт тоже надо слать пачками.

### B.4 Семантика «срока актуальности»

Когда `expires_at` прошёл — решение владельца продукта. Рекомендация: **напоминания просто прекращаются**,
плюс одно уведомление автору задачи `task.expired`; автоматическую отмену задачи сделать
опцией на самой задаче, а не поведением по умолчанию.

### B.5 RuStore Push

Транспорт — часть функции: если пуш не долетает, напоминаний нет.

**Клиент.** `react-native-rustore-push` (npm, официальный, документация rustore.ru/help/ru/sdk/push-notifications/react).
Требует запись репозитория в `android/build.gradle` и объявление messaging-сервиса в `AndroidManifest.xml`.
Это нативный модуль — под Expo нужен config plugin. Каталоги `android/` и `plugins/` в репозитории уже есть,
то есть проект на prebuild, и это выполнимо.

**Сервер.** `backend/services/push.ts` становится маршрутизатором по провайдеру токена:
RuStore (VK Push) для Android, APNs для iOS, Expo — для разработки.

**Схема.** `User.push_token` — одна строка на пользователя, этого больше не хватает: нужен провайдер
и несколько устройств.

```prisma
model PushDevice {
  id, user_id, token, provider ('rustore'|'apns'|'expo'|'fcm'),
  platform, app_version, last_seen_at, created_at
  @@unique([token])
  @@index([user_id])
}
```

Отписка «устройства больше нет» (`scheduler.ts:152`) переезжает на удаление строки `PushDevice`
вместо обнуления `User.push_token`.

**Миграция.** Некоторое время слать в оба транспорта и мерить доставку, потом отключать FCM.
iOS не затрагивается — APNs остаётся, это епархия Apple.

### B.6 Клиентский UI

- Редактор напоминания: частота, выбор времени (`@react-native-community/datetimepicker`),
  чипы дней недели, дата «актуально до».
- Локальное зеркало (`src/utils/notifications.ts:175`) **оставить только для `once`**. Повторяющиеся
  триггеры Expo не выражают правило «по Пн и Ср в 09:00 до 30 августа» надёжно на обеих платформах,
  и телефон начнёт дублировать серверный пуш.

## C. amoCRM — все три уровня

### C.1 Фундамент и ротация токена

```prisma
model AmoIntegration {
  id, organization_id @unique, subdomain,
  client_id, client_secret_enc, access_token_enc, refresh_token_enc,
  token_expires_at, connected_by, last_sync_at,
  status ('active'|'needs_reauth'|'paused'), created_at, updated_at
}

model AmoEntityMap {
  id, organization_id, entity_type ('contact'|'company'|'lead'),
  local_id, amo_id, last_synced_at, last_local_hash, last_remote_hash
  @@unique([organization_id, entity_type, amo_id])
  @@unique([organization_id, entity_type, local_id])
}

model AmoSyncOutbox { /* по образцу WebhookDelivery: payload, status, attempts, next_attempt_at */ }
```

Токены — через существующие `encryptField`/`decryptField` (`services/encryption.ts`).

**Ротация refresh-токена — то, на чём разваливается большинство интеграций с amo.** Refresh-токен
меняется при КАЖДОМ обновлении. Требования:

- новый refresh сохраняется в **той же транзакции**, что и разбор ответа;
- параллельные обновления сериализуются — advisory-lock по `organization_id`, иначе два запроса
  уйдут со старым refresh и второй убьёт доступ насовсем;
- при `invalid_grant` — статус `needs_reauth`, уведомление владельцу, **очередь останавливается**
  (долбить нельзя, это не транзиентная ошибка).

**Троттлинг.** Токен-бакет на ~5 запросов/с при потолке 7, пакеты по 250 сущностей.

### C.2 Уровень 1 — импорт

Практически клон `importBitrix24.ts`.

- `POST /api/v1/imports/amocrm` после OAuth-подключения.
- Постраничный обход `/api/v4/contacts`, `/api/v4/companies`, `/api/v4/leads` (`limit=250`).
- Кастомные поля amo → ваш `custom_fields Json`.
- Телефон/почта — через `encryptField` и `blindIndex`, как в Bitrix-импорте.
- **Обязательно писать `AmoEntityMap`**, иначе уровни 2 и 3 создадут дубликаты всего импортированного.

**Маппинг этапов.** У amo `pipelines` → `_embedded.statuses`. При первом подключении создаём воронки
и этапы amo как свои (для этого и нужна функция A), затем даём экран переназначения. Это единственное
место, где A и C жёстко связаны.

### C.3 Уровень 2 — входящий поток

- Подписка через `POST /api/v4/webhooks` с событиями `add_lead`, `update_lead`, `status_lead`,
  `add_contact`, `update_contact`, `delete_lead`.
- Приёмник `POST /api/v1/integrations/amocrm/webhook` — **сессии у него нет**, поэтому:
  - проверка подписи amo (HMAC по `client_secret`) обязательна;
  - путь добавляется в список публичных в `authenticate.ts`;
  - amo шлёт **form-encoded, не JSON** — на этот роут нужен `@fastify/formbody`.
- Обработчик тонкий: проверил подпись → положил в `AmoSyncOutbox` (`direction=inbound`) → отдал 200.
  amo повторяет при не-2xx и **отключает вебхук, который стабильно падает**.
- Применяет изменения фоновый воркер, помечая записи `origin='amo'` — см. подавление эха ниже.

### C.4 Уровень 3 — исходящий поток и двусторонность

Самый большой кусок плана — примерно равен A и B вместе взятым.

- Точки перехвата — существующие доменные мутации (`deal-domain.ts`, `contact-domain.ts`):
  ставят строку в исходящую очередь.
- Механику ретраев не изобретаем: `webhooks.ts` уже держит очередь, бэкофф и `next_attempt_at`.
  Тик amo-синхронизации становится соседом `runWebhookDeliveryTick` в `startScheduler`.

**Подавление эха** — иначе получаем бесконечный цикл. Две независимые защиты:
1. У каждой записи есть происхождение; изменения, применённые из amo, помечены `origin='amo'`
   и не ставятся в исходящую очередь.
2. `last_remote_hash` в `AmoEntityMap`: если хеш исходящего payload совпадает с последним принятым —
   отправка отменяется.

**Разрешение конфликтов** — обе стороны изменили одно поле с момента последней синхронизации.
Рекомендация: **побеждает последняя запись по времени, плюс таблица журнала конфликтов**, чтобы было
видно, что именно затёрлось, и настройка «источник истины» на уровне организации.

**Удаления** — самое неприятное. Рекомендация для v1: **исходящие удаления не транслируем вообще**,
входящее `delete_lead` переводит сделку в архив, а не удаляет.

**Сверка.** Вебхуки amo не дают гарантии доставки. Нужен ночной проход полной сверки, который лечит
пропущенные события — без него расхождение копится молча.

## D. Сквозные риски

1. **Резервных копий по-прежнему нет.** По вашему же журналу (журнал переехал в Obsidian: `Projects/CRM/SESSION_LOG_2026-08-01_self-hosting.md`)
   бэкапы ни разу не запускались, продакшен-данные существуют в единственном экземпляре на ноутбуке.
   Все три функции несут миграции и трогают боевые данные. **`pg_dump` по расписанию должен появиться
   до первой миграции.** Это самый высокий риск на странице, и он не про код.
2. Каждый новый роут обязан попасть в тесты паритета прав, иначе 45/45 перестанет что-либо значить.
3. Функции A и C связаны через маппинг этапов — порядок A → C менять нельзя.
4. B.1 (часовой пояс) блокирует всё остальное в B; делать первым внутри B.
